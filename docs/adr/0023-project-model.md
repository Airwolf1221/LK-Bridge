# ADR 0023: Several LegendKeeper projects in one bridge; exactly one bridge process per project

Status: Accepted (v2 session A1, 9 November 2026; number 0022 belongs to session B1's Markdown converter ADR, built in parallel). Implements PLAN-v2 4.1 and settled item 8.1; records the rule PLAN-v2 10.6 asks A1 to record. Retires the sandbox settings (`LK_SANDBOX_API_KEY`, `LK_SANDBOX_PROJECT_ID`) and supersedes ADR 0018 decision 7 (`--allow-bridge-project`).

## Context

v1 served one LegendKeeper project, named by `LK_API_KEY` and `LK_PROJECT_ID`, with a separate sandbox key for the test scripts. v2 serves at least two at once: Arkona (the live world) and the test world. LegendKeeper keys are per project, and so are its rate tiers (per key) and its project tier. Every stored record (jobs, journal, proposals, errors, budget samples, mappings, maintenance runs, governor counters) was implicitly "the one project".

Two facts constrain the design:

- the bridge's locks (per document and per resource, chunk 2) and its writer pool live in the process;
- LegendKeeper's `If-Match` check is not an atomic compare-and-swap: overlapping writes with the same expected version can both be accepted (PLAN-v2 10.6).

## Decision

1. **Where things live.** Secrets stay in the env file: `LK_PROJECTS` (comma-separated names), `LK_PROJECT_<NAME>_API_KEY` per project, `LK_DEFAULT_PROJECT`. Everything else lives in the `projects` table: the name, the LegendKeeper project id, LegendKeeper's display name, `is_default`, `is_sandbox`, `read_only`, and JSON `settings` read through a typed accessor (`src/projects/settings.ts`; AI REPOSITORY root, Characters root, chronology resource, template ids). The settings are shown read-only on the dashboard in this release; the tools that need them (B and C sessions) add their editing.
2. **The project id IS the LegendKeeper project id**, discovered from the key: at every start each key lists its projects (`listProjects`, through that project's own governor) and must see exactly one. A new name is registered with the id its key proves. A stored project whose key now answers for another id is **stopped**, not re-pointed: its rows keep their id, and the owner decides. A refused key (401, 403) or an unpaid plan (402) also stops that project; an unreachable LegendKeeper leaves it `unverified` and retried (15 s, doubling to 10 minutes). A stopped or unverified project is refused with `PROJECT_UNAVAILABLE`; the others are served. The bridge listens at once and serves each project from the moment its own check passes. Keys are never logged or shown: only the name of the variable holding one.
3. **The single-project form still works.** Without `LK_PROJECTS`, `LK_API_KEY` and `LK_PROJECT_ID` become one project named `LK_PROJECT_NAME` (default `test`), whose key must belong to `LK_PROJECT_ID`, with a start-up warning that names the variables to move to. The runbook has the move.
4. **One governor per project**, with its own counters persisted per project (`governor_counters`, keyed by project). The writer pool stays **global** (`WRITERS_MAX` is the bridge's own concurrency, not LegendKeeper's), with **fairness across projects**: when a slot frees, projects with waiting writes take turns (round-robin), and within a project writes keep their order. Exhausting one project's tier never delays another's calls.
5. **Every LK-data row carries a required `project_id`** (migration 0600). Child tables reference their parent by `(id, project_id)`, so a child can never belong to another project than its parent. Existing rows are assigned to the project the bridge served before, whose id the migration takes from `LK_PROJECT_ID` (the deploy script passes it); a database with data and no such id is refused before anything changes. Every query takes a project, or the explicit `ALL_PROJECTS` value (`{ allProjects: true }`, never `undefined`), so "all projects" is always a visible choice in code. Locks are keyed by project and entity (`<projectId>:doc:<id>`). Bridge-wide maintenance runs (journal and proposal pruning, proposal expiry, the SQLite optimise and the budget sampler, which samples every governor) are recorded with project `*` and are not engine jobs; per-project maintenance jobs run once per served project.
6. **Exactly ONE bridge process may serve a project.** The locks above are in-process, and `If-Match` cannot stand in for them; two processes serving the same project could overlap writes to the same page and lose one. Making locks database-held is a later decision (it would need its own ADR). The rule is enforced for the case that can happen by accident, a second process on the same database (a second `systemd` unit, a manual `node dist/server.js` while the service runs): the `bridge_instance` row names the one process allowed to serve the database, with a heartbeat every 15 seconds, and a second process is refused at start-up (`INSTANCE_LOCKED`, naming the holder's pid, host and start time). A holder is taken over only when it is provably gone: on the same host, its pid no longer exists or it has not beaten for 60 seconds; on another host, its heartbeat is 60 seconds old. Two bridges with **separate** databases and the same key cannot see each other; the runbook forbids it (one key belongs in one env file).
7. **The `project` argument.** Every MCP tool takes an optional `project`: a name (any case) or a LegendKeeper id mapped back. Unknown: `UNKNOWN_PROJECT` with the registered names. Reads without it use the default project. Writes without it are refused with `PROJECT_REQUIRED` when more than one project is registered (`REQUIRE_PROJECT_FOR_WRITES=true`, the default, settled item 8.1), at scope `propose` too. Every result names its project and ends with that project's budget line (`budget (arkona): …`); a refused `project` carries the default project's line. `list_projects` shows name, id, display name, default and read-only flags and availability: never a key, and **not** the sandbox flag, which is an operator concern (the scripts' target), not something an agent should choose by.
8. **Policy is unchanged.** Profiles and scopes stay per connection, across projects (PLAN-v2 4.1 does not ask for per-project scopes); every listing is filtered by the asked project. A proposal records its project, is shown only in it, and its approval executes against that project only (an approval asked from another project is "not found").
9. **Read-only per project.** The project's `read_only` flag can only make it stricter: a project is read-only when the bridge is, or when its own flag is set. It is edited on the dashboard's Projects page (with a confirmation, audited as `project.set_read_only`) and stored on the project row, so it survives restarts.
10. **Sandbox.** `LK_SANDBOX_API_KEY`, `LK_SANDBOX_PROJECT_ID` and `--allow-bridge-project` are removed. The sandbox, soak and spike scripts take `--project <name>`, use that project's key from the env file, and refuse any project not marked `is_sandbox`. The flag is set only from the server's shell (`npm run projects -- sandbox <name> on`, audited `project.set_sandbox`), never from the dashboard: one click must not be able to turn Arkona into a test target. The dashboard shows it read-only.

## Consequences

- An agent working in two projects names each write's project; a forgotten argument is refused rather than written to the default (which will be Arkona).
- Data never crosses projects by construction (composite foreign keys) and by query (every query is scoped); `test/projects/` checks every surface with two mock projects running at once.
- A project with a bad key no longer stops the bridge: it shows as stopped on the Overview and the Projects page, and the other projects carry on.
- Running two bridges for one project is refused on one database and documented as forbidden otherwise. Lifting the rule needs database-held locks and a new ADR.
- The single-project env form is deprecated but supported; the migration needs `LK_PROJECT_ID` once, which the deploy script supplies from the env file.
