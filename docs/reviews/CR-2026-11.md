# CR-2026-11: mid-point review of the write layer

An independent review of the write layer as merged on `main` at `08feec9` (11 November 2026): C1 `write_page` (ADR
0031), C2a `set_facts` and the canon guard (ADR 0032, with the C2a.1 rank-order hotfix), C2b's resource, document and
character tools (ADR 0034), C2c's page lifecycle (ADR 0035), the connections hotfix (ADR 0033), the bulk-canon hotfix,
and the engine underneath them: jobs, locks and the writer pool, the bridge's own steps, proposals, the journal and the
governor's retries.

**How it was done.** The reviewer did not write the code and treated every "verified", "tested" and "covered" in the
earlier reports, the changelog and the ADRs as a claim to check. The engine, journal, proposals, locks, failure paths
and budgets were read in full. Four separate reviewers, each in an isolated copy of the repository and each given the
code rather than the reviewer's conclusions, tried to break the canon guard, the lifecycle guard and the write routes'
security, and listed every assumption the tests make about LegendKeeper. Every finding below was reproduced by a test
that asserts the safe behaviour and **fails on the old code**; each fix makes it pass. **Nothing was run against a live
system**: every test runs against the mock LegendKeeper in this repository, and the bridge's LegendKeeper connector was
not called. The sandbox tests of section 6 are written, not run; the owner runs them.

**Severity:** critical — could lose or corrupt data, or pass canon or lifecycle approval; high — a wrong result or a
misleading state; medium — cost or robustness; low — clarity.

### CR-01 (High): deletes LegendKeeper cannot undo kept only ids

- **Found by:** reading `src/jobs/op-meta.ts` against the spec. `deleteProperty`, `deleteEvent`, `deleteFeature`,
  `deleteLane` and `deleteAsset` journalled only ids (`gone(…, 'ids')`), as PLAN §6.4 does for deletes, on the
  assumption that deletes are soft. They are not all soft: LegendKeeper has `restoreResource` and `restoreDocument`, and
  nothing else. A deleted sidebar property (the PROPERTIES facts, a link collection) could not be restored from the
  journal or anywhere else.
- **Fix:** those five deletes read the entity before the delete inside the lock and keep it as the pre-image (one more
  read each). A lane's pre-image is the lane alone (its events are not read: open for D1, section 7); an asset's is its
  record (not its bytes, nor a folder's contents: open for D3 and E1).
- **Test:** `test/facts/cr-property-loss.test.ts` ("a property delete keeps a pre-image the owner can restore from"):
  the journal entry of a deleted link collection holds its items and filter. `test/assets/after-write.test.ts` counts
  the asset delete's new read.

### CR-02 (Critical): `unsupported` sidebar content could be dropped

- **Found by:** reading the spec: a sidebar property can be `unsupported` itself (TAGS on every `[BSRC]` page) or hold
  `unsupported` blocks (a text field's `children`); so can an infobox property. The unsupported-block guard (PLAN §4
  rule 2; CLAUDE.md: never drop them) covered only document and block operations. `deleteProperty` of TAGS, or an
  `updateProperty` with new `children`, lost them for good, unguarded.
- **Fix:** a third guard kind, `property` (`unsupportedGuardSides`, src/jobs/guards.ts), on `deleteProperty`,
  `updateProperty`, `deleteBlockProperty` and `updateBlockProperty`: a delete loses the property itself when it is
  `unsupported` and every `unsupported` block under it; an update loses only what its new `children` leave out (an update
  that sends no children keeps them). Refused with `UNSUPPORTED_BLOCK_LOSS` unless the caller passes
  `allowUnsupportedLoss`, at the proposal's capture and inside the lock. The proposal detail shows the loss the same way.
- **Test:** `test/facts/cr-property-loss.test.ts` (5 tests: TAGS, a text field with an unsupported block, a lossy and a
  safe `updateProperty`, and the deliberate delete with its pre-image). The sidebar mock now models a text field's
  children (`test/facts/sidebar-model.ts`).

### CR-03 (Medium): lifecycle jobs read more than they need

- **Found by:** listing every read of an accepted `archive_page` against the mock (19 reads): the canon and lifecycle
  guards each read the same sidebar at entry, seconds after the approval had read the page; and the repository tree
  re-read the page after the rename, after the move, and again when the job ended.
- **Fix, without dropping a check:** the approval hands its re-read of each captured page (a `getResource` carries the
  sidebar) to the entry guards as `prefetched` (src/policy/proposals.ts); the lifecycle job's rename and move carry
  `deferTreeReread`, so the tree re-reads the page once, at the end, with the facts. Every check inside the lock, the
  job's own check step and the verify step are unchanged.
- **Test:** `test/lifecycle/costs.test.ts`: every lifecycle job is 4 reads cheaper (19 → 15 for `archive_page` and
  `unarchive_page`, 15 → 11 for `move_to_working` and `promote_page`), and every lifecycle test still passes.

### CR-04 (Medium): held writes starved a job that could run

- **Found by:** reading `pumpNow` (src/jobs/engine.ts): it looked only at the first `maxActiveJobs + 100` queued jobs.
  While writes are paused (or a project is read-only), every write job is held; with more held jobs than that ahead of
  it, a job whose next step reads never started. A sibling of C2a's paused-loop bug.
- **Fix:** the scheduler walks the ids of every queued job, in order, until its capacity is used (`queuedJobIds`).
- **Test:** `test/jobs/cr-held-backlog.test.ts`: 112 held write jobs, then a read job, with writes paused: the read job
  runs.

### CR-05 (High): a stopped multi-operation proposal ended `failed`

- **Found by:** reading `onJobFinished` (src/policy/proposals.ts): a proposal becomes `conflicted` when its job's check
  inside the lock refuses it and nothing was written (ADR 0031 decision 8), but only for `write_page`'s single
  `operation`, and only when no step at all had succeeded. Lifecycle, C2b and set_facts proposals carry `operations`, and
  their check and record steps succeed before any write, so a change after the approval's re-read ended the proposal
  `failed`, a final state that says the writes went wrong.
- **Fix:** every high-level proposal (`operation` or `operations`), and "nothing written" judged by the job's
  LegendKeeper writes (none succeeded, none may have been sent).
- **Test:** `test/lifecycle/cr-conflicted.test.ts`: an accepted `archive_page` whose page is tagged in the app between
  the approval and the job's check ends `conflicted`, nothing written.

### CR-06 (High): a job held after its check wrote over an outside edit

- **Found by:** reading `runJob`. A job holding its page's lock checks the page (`bridge.expect`) and then writes. When
  it is held (writes paused, read-only), parked for budget, paused or restarted after the check and before its first
  write, it releases the lock; when it takes it again the check has already succeeded and is not run again. An edit
  made meanwhile was overwritten: for example a lifecycle job's `updateResource` replaced the tags with the list planned
  before the edit.
- **Fix:** when a job takes its job-level lock again and nothing has been sent yet, its succeeded checks run again
  (`recheckOnRelock`). Once a write has been sent the check is not repeated (the job's own writes changed what it
  checked); the writes after it carry their own checks, as before.
- **Test:** `test/lifecycle/cr-resume-after-hold.test.ts`: writes paused right after the check, the page's tags edited
  in the app, writes resumed: the job stops on `VERSION_CONFLICT` and the edit survives; with no edit, it checks again
  and writes as planned.

### CR-07 (High): an unknown outcome was reported as "Nothing was written"

- **Found by:** reading the tools' failure summaries (src/mcp/tools/set-facts.ts and write-job.ts). A write whose
  answer was lost and whose check could not tell is `uncertain`: it may have been made. set_facts answered "Nothing was
  written: …the write may have applied…", and the resource tools listed it under `notWritten`. An agent could repeat a
  change that had been made, or tell the owner nothing changed when it had.
- **Fix:** such a write is reported as `OUTCOME_UNKNOWN` with an `uncertain` list, never as not written; the hint says
  to read the pages first and not repeat the call.
- **Test:** `test/facts/cr-unknown-outcome.test.ts` (set_facts and update_resource: the write applies, every answer and
  the check's read fail; the answer is `OUTCOME_UNKNOWN`, and the value was in fact written).

### CR-08 (Critical): a caller's If-Match, and `continue` batches, passed both guards

- **Found by:** the canon, lifecycle and security reviewers independently. Two gaps together:
  - inside the lock, both guards skipped any row write that carried an `If-Match` the engine had not read, trusting
    LegendKeeper's version check to refuse it if the rows had changed since the entry check;
  - the entry check simulates a batch on the assumption that every step before a write succeeded, and seeds a template
    copy's id with the template's sidebar. With `onError: "continue"`, a step that fails (a template copy given an
    existing page's id, a row delete with a stale version) leaves the simulation describing a page that does not
    exist, and the next steps still run.
    So `lk_api_batch` with a failing first step and an `updatePropertyRow` carrying the version the agent had read changed
    Status Authoritative → anything (or to Authoritative, or Working → Authoritative) at scope `write`, with no proposal.
- **Fix:** inside the lock, only a row write whose `If-Match` the engine chained from the job's own previous write
  (`ifMatchFrom`) is left to LegendKeeper; a caller's version is read and judged like any write. At entry, each write of
  an `onError: "continue"` batch is also judged on the page as it is now.
- **Test:** `test/facts/cr-canon-bypass.test.ts` (F1, F1b), `test/lifecycle/cr-canon-bypass-tree.test.ts` (F1c, F1d),
  `test/lifecycle/cr-guard-bypass.test.ts` and `test/lifecycle/cr-lifecycle-bypass.test.ts` (F3).

### CR-09 (Critical): cascade deletes removed Authoritative pages without approval

- **Found by:** the canon and security reviewers. The pages of a cascade came from the repository tree (which may be an
  hour behind, or `stale`), and inside the lock only the top page was read again. An Authoritative page added or moved
  under the deleted page in the app, or moved there by an earlier step of the same batch
  (`[moveResource(canon → box), deleteResource(box, cascade)]`), was deleted without canonical approval.
- **Fix:** the subtree is listed live at entry and again inside the lock, and every page's sidebar read in both (at most
  101 pages; more, or a listing that fails, needs canonical approval). A cascade in a request that also moves, restores
  or creates pages counts as unchecked (a canonical proposal). A cascade of N pages now costs about 4N reads.
- **Test:** `test/lifecycle/cr-canon-bypass-tree.test.ts` (the batch and the outside race),
  `test/lifecycle/cr-guard-bypass.test.ts` (a page the tree has not seen). The spike's dry-run fixture lets the guard's
  in-lock listing through as it already did its entry listing (`test/tools/spike-world.ts`).

### CR-10 (Critical): a template copied with its children was judged by its top page

- **Found by:** all three guard reviewers. `createResourceFromTemplate` with `includeChildren: true` copies every page
  under the template with its sidebar and name. Both guards judged only the top template: a template with an
  Authoritative child (an agent can make one with `saveResourceAsTemplate`, or by moving a canon page under a template
  in the same batch) created new Authoritative pages, `[BARC]` pages outside the archive, and a second
  `[INDEX] Archived`.
- **Fix:** with `includeChildren`, every page under the template is listed live and judged as a new page, by both
  guards, at entry and inside the lock (at most 100; more, or unreadable, is refused or proposed). A template saved from
  a page earlier in the same request is judged on that page. A copy with its children in a request that also moves,
  restores, creates or saves pages counts as unchecked.
- **Test:** `test/lifecycle/cr-canon-bypass-tree.test.ts` (F5 and the harmless copy that must still be written),
  `test/lifecycle/cr-guard-bypass.test.ts`, `test/lifecycle/cr-lifecycle-bypass.test.ts` (F1).

### CR-11 (Critical): a Status written as a page mention

- **Found by:** the canon and lifecycle reviewers. `valueText` reads a mention as its `text`, else its `name`, else the
  page id; the spec says a run's `name` is read-only (LegendKeeper fills in the page's current name). So
  `updatePropertyRow(Status, [{ mention: { resourceId: X, name: "Authoritative" } }])` was judged as the agent's text, and
  a label-less mention of a page named "Archived" as its id; LegendKeeper then showed, and the bridge then read, the real
  name. Renaming the mentioned page later changed the Status with no sidebar write at all.
- **Fix:** a new page mention in a fact a `value` rule names (Status) is a protected change for the canon guard, and a
  refusal for the lifecycle guard (write the Status as plain text). ADR 0036 decision 2.
- **Test:** `test/facts/cr-canon-bypass.test.ts` (F2: forged name, label-less mention, rename of the mentioned page),
  `test/lifecycle/cr-lifecycle-bypass.test.ts` (F2).

### CR-12 (Medium): look-alike keys and values

- **Found by:** the canon reviewer: `factKey` and `factValueKey` only trimmed, collapsed spaces and lower-cased. A row
  keyed `Status​` (zero-width space), `Ｓｔａｔｕｓ` or `Statуs` (Cyrillic у), or valued `Authori‍tative` or with a
  soft hyphen, showed as "Status: Authoritative" and was judged as an ordinary fact.
- **Fix:** keys and values are folded before comparison (src/facts/rules.ts): NFKC, Unicode's default-ignorable
  characters removed, then Cyrillic and Greek look-alikes read as the Latin letters they look like.
- **Test:** `test/facts/cr-canon-bypass.test.ts` (F3, six cases).

### CR-13 (Critical): lifecycle moves judged from the tree only

- **Found by:** the lifecycle and security reviewers. A move's "from" and "to" areas came from the repository tree, at
  entry and inside the lock. A Working or Archived page the tree had not seen yet (made or moved in the app) could be
  moved out of its area; and moving `[INDEX] Working` out of the AI REPOSITORY made the tree forget its pages, which
  could then be moved out before the index was moved back.
- **Fix:** inside the lock the page's area comes from its parent as LegendKeeper holds it now (the engine's own read);
  a parent the tree does not know is read up to its ancestors; an area that cannot be told counts as a crossing. At
  entry the tree is used when it knows the page, else a read. (The index move itself is CR-15.)
- **Test:** `test/lifecycle/cr-guard-bypass.test.ts`, `test/lifecycle/cr-lifecycle-bypass.test.ts` (F4, F7).

### CR-14 (High): look-alike lifecycle prefixes

- **Found by:** the lifecycle reviewer. The tree classifies a prefix exactly; the guard used the same classification,
  and a rename from `[BSRC]` to an unclassified name is not a lifecycle change. `[barc] X`, `[BARC]X`, a zero-width space
  first, `[BARC]` and a no-break space, fullwidth brackets and a Cyrillic А all renamed an Authoritative page into one a
  reader takes as archived, with Status Authoritative still. If LegendKeeper trims names, ` [BARC] X` became a real
  `[BARC]` page.
- **Fix:** the guard reads prefixes loosely (`looseKind`: the folded name, any case, optional space, leading invisible
  characters), for renames and creates.
- **Test:** `test/lifecycle/cr-lifecycle-bypass.test.ts` (F8, F9).

### CR-15 (Critical): the lifecycle indexes themselves were unprotected

- **Found by:** the lifecycle reviewer. Renaming `[INDEX] Working` stopped every lifecycle tool and every default Working
  create (`LIFECYCLE_INDEX_CHANGED`) and let a decoy be "found"; deleting it with a cascade deleted every Working page
  without approval (no rule protects Working pages), and restoring one of them put it at the root, out of Working.
- **Fix:** renaming, moving or deleting a confirmed lifecycle index, and creating or renaming another page to a
  lifecycle index's name, are refused (the owner changes them by hand and confirms them again). ADR 0036 decision 3.
- **Test:** `test/lifecycle/cr-lifecycle-bypass.test.ts` (F5, F6, F7).

### CR-16 (High): `[BSRC]` pages made by raw routes

- **Found by:** the lifecycle reviewer. ADR 0035 decision 5 makes an Authoritative create through the creation tools a
  canonical proposal; `lk_api_write createResource { name: "[BSRC] …" }` wrote one directly at scope `write`, and a
  rename from a plain name to `[BSRC] …` likewise.
- **Fix (proposed to the owner, ADR 0036 decision 1):** a create or rename into `[BSRC]` that no creation or lifecycle
  tool declares becomes a canonical proposal at every scope.
- **Test:** `test/lifecycle/cr-lifecycle-bypass.test.ts` (F10). Three proposal tests that create `[BSRC]` pages through
  `lk_api_write` now accept them as canon (`test/facts/proposals.test.ts`).

### CR-17 (Critical): template copies half judged by the lifecycle guard

- **Found by:** the lifecycle reviewer. A copy given no `name` takes the template's (LegendKeeper names it), but the
  guard judged an empty name; a template's Status was judged only when the caller gave the copy an `id` (the engine
  mints one after the guard has run). `saveResourceAsTemplate` of a `[BWRK]` page and a copy of it without a name made a
  `[BWRK]` page with Status Working outside Working.
- **Fix:** a copy without a name is judged by the template's name (read, or the page a template was saved from earlier
  in the same request), at entry and inside the lock; a template's Status is judged whether or not an id was given.
- **Test:** `test/lifecycle/cr-lifecycle-bypass.test.ts` (F1).

### CR-19 (Low): an agent could cancel approved work part-way

- **Found by:** the security reviewer. An approved proposal's job runs as the agent that proposed it (so its budget and
  scope apply), and `bridge_job_cancel` checks only the principal. Cancelling a lifecycle job part-way leaves a
  half-made change the owner approved as a whole.
- **Fix:** `bridge_job_cancel` refuses a job the owner approved (`OWNER_APPROVED_JOB`); the owner cancels it on the
  dashboard.
- **Test:** `test/facts/cr-approved-cancel.test.ts`.

## 3. What was checked and found sound

So later sessions know what has been reviewed. Each was checked by reading the code and, where noted, by the existing or
new tests.

**Data loss.** The unsupported-block guard walks every depth of a document, a block and (now) a property, at capture,
before the write inside the lock, and in the proposal detail; `write_page` offers no way round it and keep regions are
refused when missing (ADR 0031). set_facts echoes every collection item it reads with its id and rank and never sends
the filter (src/facts/plan.ts), so items a filter adds are kept and link item ids and order survive; rows are compared
by id in rank order. Every destructive write is journalled before it is sent, with its outcome settled after.

**Version checks.** Every versioned write sends If-Match: the engine refuses one with no version, and the governor
refuses a versioned write without the header (`IF_MATCH_REQUIRED`). The bridge's own compare-and-swap inside the lock
covers each case LegendKeeper's If-Match does not: sidebar rows and collections (`bridge.expect`, and `expectCurrent`
on `updateProperty` and on a row write with nothing to chain from), template copies (`copy`), blocks (`block`) and the
whole sidebar for `baseFactsVersion` (`sidebar`). Chained row writes take their If-Match from the write before; a
re-send after an ambiguous failure uses the version it was first sent with, so LegendKeeper refuses it if anything
changed. Races were tried at each point: between plan and lock (the check; for proposals, the approval's re-read and the
check), between lock and write (the in-step reads), between chained writes (LegendKeeper's If-Match with the job's own
versions), and across a lock released mid-job (CR-06).

**Canon.** Approval tokens are bound to the proposal, principal, project, step index, operation and params hash, are
consumed, and expire; the ordinary and bulk approvals refuse a canonical proposal and "accept as canon" refuses an
ordinary one; a tampered expansion is refused at execution with nothing written; the system principal is refused a
protected change; `createResource` and `createManyResources` cannot carry properties (`additionalProperties: false`).
Plain step-by-step `lk_api_batch` sequences (renaming a key to Status, a second Status row, Status in a second
key-value property, deleting and re-creating the row) are caught by the simulation.

**Lifecycle.** The marker is set only by bridge code and stored with the job and the proposal's job options; a marker
cannot cover pages other than those it names; two-step batch moves ("into X, then X under Working"), nested creates and
moves into a nested child of an index are refused; a resume plans from the record and is a new canonical proposal.

**Proposals.** Ids are minted at capture and approval submits exactly the stored params; every guard runs again at
execution; `conflicted` proposals can only be rejected; `pending`, `approved`, `executing` and `conflicted` are never
pruned; bulk approve, bulk accept-as-canon and bulk reject act on at most 100 ids, each on its own, with `confirm: true`
for canon, and an id from another project fails the whole request (`test/admin/cr-proposal-routes.test.ts` pins this).

**Concurrency.** Deadlock is impossible: a step takes its lock before its writer slot and a slot holder never waits for
a lock; a job holding several job-level locks takes them in sorted key order before its first step and holds no other
lock while it waits; waiters are served first come, first served; the writer pool takes projects in turn. `operation_id`
is reserved in one SQLite transaction (two identical calls at once: one runs, the other is `OPERATION_IN_PROGRESS`);
character claims count across principals.

**Failure and resume.** Lifecycle writes are ordered so a stop never makes a page look more canonical than it is
(leaving canon renames first; entering canon renames last). Each multi-write job reports what was written, what was not,
and now what is uncertain (CR-07). A step that may have been sent is verified before anything is re-sent, by its kind
(client id, gone, state, idempotency key); a `createManyResources` stopped part-way re-sends only the missing items.

**Budgets.** The governor holds P3 back while any P1 or P2 work is queued (governor.ts:581) and keeps half of each tier
from P3, so the link sweep and the tree's passes cannot starve agents; the link sweep also waits while agent work is
queued and parks on budget. Verify steps of batches read each parent's listing once (100 siblings a read).

**Security of the write routes** (the security reviewer's table, condensed). Every `/api/admin` route added since v1.0.2
is owner-only, refuses bearer tokens, and checks Origin, CSRF and `Sec-Fetch-Site` on every non-GET
(`test/admin/auth.test.ts` walks them all); no GET changes state; the dashboard renders agent text without
`dangerouslySetInnerHTML`. Every MCP write tool resolves its project for writing (so `REQUIRE_PROJECT_FOR_WRITES`
applies), honours scope (read refused, propose proposed, write run; the lifecycle tools always propose) and has the
right access annotation. No field only bridge code may set is reachable from an agent: tool inputs are parsed by zod,
`lk_api_batch` maps only `allowUnsupportedLoss` and `confirm` into step options and refuses `bridge.*` operations, the
bridge's own steps need `internal`, which only the tools set, and proposals keep step options through an allow-list.
Read tools show only the caller's own jobs and proposals; `bridge_journal_lookup` shows every principal's writes by
design.

## 4. Restoring from the journal

What the owner does, by hand, to undo each kind of destructive write (`bridge_journal_lookup`, or the dashboard's
journal, gives the entry and its pre-image):

| Write                                                      | Pre-image                                                 | How to restore                                                                                                                                                       |
| ---------------------------------------------------------- | --------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `replaceDocumentBlocks` (`write_page`)                     | the document's blocks and version                         | `replaceDocumentBlocks` with the pre-image's blocks (its `unsupported` blocks are still on the page, so echoing them by id keeps them); If-Match the current version |
| `replaceBlock`, `deleteBlock` (the archive note's removal) | the block and its subtree                                 | `insertBlock` with the pre-image; its place (after or before a sibling) is not recorded and is found from the page (the lifecycle note: first block)                 |
| `updateResource` (renames, tags; lifecycle renames)        | the resource: name, tags, aliases, rank, …                | `updateResource` with the old name and tags                                                                                                                          |
| `moveResource` (lifecycle moves, re-placing renames)       | the resource with its old `parentId` and rank             | `moveResource` to the old parent, `after` or `before` the sibling the old rank sat next to                                                                           |
| Row writes of set_facts and the lifecycle tools            | the whole key-value property before the job (first write) | `updatePropertyRow` / `createPropertyRow` / `deletePropertyRow` back to the pre-image's rows (keys, values, in rank order)                                           |
| `updateProperty` (a link collection)                       | the property with its items and filter                    | `updateProperty` with the pre-image's items (ids and ranks); the filter is never sent, so it is kept                                                                 |
| `deletePropertyRow`                                        | the row (key, value, rank)                                | `createPropertyRow` with the key and value, `after` the row that preceded it                                                                                         |
| `deleteProperty` (CR-01)                                   | the property: rows, items, filter, children               | `createProperty` with the same kind, title, rows or items and filter (new ids). An `unsupported` property (TAGS) cannot be recreated: the guard refuses its delete   |
| `deleteResource` (with or without cascade)                 | ids                                                       | `restore_resource` (`restoreResource`): brings back the page and every page deleted by the same delete, with its documents and properties                            |
| `deleteDocument`                                           | ids                                                       | `restoreDocument`, in its old place, with its content                                                                                                                |
| `deleteEvent`, `deleteFeature` (CR-01)                     | the event or feature                                      | `createEvent` / `createFeature` with the pre-image's fields                                                                                                          |
| `deleteLane` (CR-01, partial)                              | the lane only                                             | `createLane`; its events are not in the pre-image (open for D1, section 7)                                                                                           |
| `deleteAsset` (CR-01, partial)                             | the asset's record                                        | re-upload from a backup (E1); the bytes, and a folder's contents, are not in the journal                                                                             |
| Lifecycle tools                                            | each write as above, plus the lifecycle record            | `unarchive_page` (or the matching tool) reverses a completed change from the record; a stopped one is resumed by calling the same tool again                         |

## 7. Open items

**For the owner** ([ADR 0036](../adr/0036-cr-2026-11-owner-decisions.md)): confirm or change decisions 1 to 3, which
are implemented (raw `[BSRC]` creates as canonical proposals; Status as a page mention refused; the lifecycle indexes
changed only by hand); decide 4 (re-authentication for the canon rules and lifecycle settings, recommended), 5 (bind a
canonical approval to the pages it listed), 6 (map, timeline and board content deletes, before D1 and D2) and 7 (guard
the status tags).

**Accepted or for a later session:**

- **Lanes and assets (D1, D3, E1).** A lane's delete keeps the lane but not its events; an asset's delete keeps its
  record but not its bytes or a folder's contents. D1's timeline tools should read a lane's events before deleting it;
  E1's snapshots cover images.
- **A lifecycle area from a stale tree's ancestors.** A move is judged from the page's parent as LegendKeeper holds it,
  but a parent the tree knows is placed by the tree's path. An index moved under Working in the app, before the tree's
  sweep, is not seen as inside Working. The areas are flat (pages sit directly under the index), so this needs an
  owner's own app edit first.
- **A restore after the owner deletes an index in the app.** LegendKeeper restores a page whose parent is gone at the
  root. The bridge cannot delete the indexes any more (CR-15); the owner restores the index first.
- **A document delete's type comes from the tree** (`deleteDocumentInLock`). A document converted from blank to a map
  in the app, before the tree's sweep, is judged as blank. Low; D2 can read it in the lock.
- **Duplicate Status rows.** The rules count every row, while the lifecycle tools read the first. A page with two
  Status rows is judged by both views, which may disagree; E2's audit should report such pages.
- **A re-send after recovery skips the guards.** Only when LegendKeeper's version is unchanged since the first send
  (so nothing changed), or with the same idempotency key inside its window. Low.
- **`DUPLICATE_REQUEST` names another connection's job or proposal.** The ids cannot be used by that connection (the job
  and proposal tools filter by principal). Information only.
- **A claim being planned counts for five minutes.** A create that plans for longer (a long budget wait) lets a second
  request for the same character through. Low.
- **Node 24.** CLAUDE.md and `package.json` ask for Node 24; this review ran on Node 22.23 (the environment's); every
  test passes there.
- **The sandbox checks** (section 6) are unconfirmed until the owner runs them.

## 8. The sandbox run (for the owner)

```bash
DB_PATH=… LKB_ENV_FILE=/path/to/lk-bridge.env LKB_SANDBOX_PROJECT=test npm run test:sandbox -- assumptions
```

On the server: `deploy/sandbox-test.sh --project test` (it runs the smoke script too). It refuses to run unless `test`
is a registered sandbox project and the key's own project is exactly that one. It creates one throwaway root
(`lk-bridge assumptions <time>`) with about 60 plainly named pages under it, three templates (`lk-bridge assumptions
template A1`, `… A2` and `… H1`, the last with one page under it), and documents, rows, a link collection and a text
field on its own pages; it deletes all of it at the end, even after a failure, and names any id it could not delete.
Cost: about 100 writes and up to about 500 reads, plus up to 12 search polls; a few minutes. It prints PASS, FAIL or
INCONCLUSIVE per assumption with what LegendKeeper answered, and fails if any assumption FAILs. Send the report back:
each FAIL is a place where the bridge's behaviour on the real API differs from what this review relied on.
